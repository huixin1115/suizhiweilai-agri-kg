# 农业知识图谱集成说明

> 面向「基层农业从业者问路无门」赛题的知识图谱增强改造。
> 技术在原有 Flask + Neo4j + RAG 基础上增量扩展，**原有功能与数据全部保留、未被覆盖**。

---

## 一、本次集成做了什么

| 层面 | 内容 |
|---|---|
| **数据** | 新增 669 节点 / 3440 条关系的农作物扩展图谱，与原有 2552 条三元组融合为 **1320 节点 / 5693 条关系**（14 类实体、22 类关系） |
| **数据质量** | 农药/农艺措施分离（不再把"轮作倒茬"当成农药）、杂草单列（不再把"看麦娘"当成病害） |
| **查询能力** | 新增 11 个图谱查询方法：实体画像、N 跳子图、模糊检索、生育期时间轴、水肥素材、防治素材、条件筛选、产区规划、规模统计 |
| **决策能力** | 新增 `AgriAdvisor` 顾问引擎，输出**四类处方**：病虫害防治建议 / 水肥调控处方 / 农事管理方案 / 生产规划报告 —— **四类各自独立成页**，侧栏直接进入，不必先想清楚问题属于哪一类 |
| **主动提醒** | 新增 `PhenologyEngine` 物候引擎：填一次播种日期，之后每天自动算出"今天处于哪个生育期、该干什么、要防什么"（52 个作物 × 5~7 个阶段，含提前 5 天预警） |
| **土质联动** | 地块可填土质（30 种土壤）：按质地/肥力/保水性给差异化管理——沙土少量多次、黏土防渍；并自动核对"这块地适不适合种这个作物"。**酸碱度改由农户自己填**（图谱值只是土类大致范围，页面不再显示），填了才给调酸/调碱建议 |
| **地块档案** | 新增 `user_plot` 表（首次使用自动创建），记住"我家的地"，打开即见当日提醒；支持**按已种植天数反推播种日期**（补录地块不必记得准确日期）；可选填**土壤 pH**（0~14，后端校验） |
| **主动触达** | 侧栏新增「今日待办」（`/todo-page`，带推荐标记）：把各块地的当日提醒按紧迫度分成**需要处理 / 生长正常 / 未播种·已结束 / 今日已完成**四组，主推"今天先管哪块地"；卡片上还能**勾选「今日已完成」**（按天记，落 `plot_task_log` 表），勾上就挪到最后一组、概览同步 +1，点卡片仍可弹出完整提醒（免去"要先点进物候页"） |
| **历史记录** | 侧栏新增「历史记录」（`/history-page`）：每次提问与四类处方**自动留痕**（问题 + 图谱答案 + 大模型答案 + 知识溯源），支持类型筛选、关键词搜索、展开全文、看溯源、再问一次、单条删除与一键清空；四张表（`qa_history` / `qa_feedback` / `user_behavior` / `hot_content`）**首次使用自动创建**，MySQL 不可用时整块降级（统计与筛选隐藏并说明原因，**提问照常出答案**） |
| **导出与数据统计** | 历史记录可**导出 Word / PDF**（复用处方那套 `core/exporter.py`，按当前筛选导出，管理端导出的是名下用户端的记录并标明是谁问的）；页面顶部还有**数据统计四张图** —— 柱状图（各类型记录数；管理端看各用户端）、折线图（近 14 天提问趋势）、饼图（类型占比）、词云（问题高频词：拿图谱里的作物与病虫害名去问题里数） |
| **经济效益测算** | 新增 `/econ-page`「经济效益测算」：填「预期亩产 + 收购价 + 七项亩成本（种子 / 化肥 / 农药 / 机械作业 / 人工 / 灌溉 / 其他）」，自动算出**亩均与总额的收入·成本·净收益**、投入产出比，以及**保本收购价与保本亩产**（"价格跌到多少就白干"）；多个作物摆在一起按**亩均净收益**排序 + 柱状图对比，帮农户决定"种啥更划算"。作物清单取**图谱全集**（与知识问答、四类处方同口径，不受管理端授权限制 —— 决策就该能自由比较） |
| **用户反馈** | 问答页与四类处方页的答案下方都有「**有帮助 / 没帮助**」：点"没帮助"可展开写清哪里不对（选填），提交后落进 `qa_feedback` 并在历史里回显"我的纠错"。这是"评价 → 改进"这条闭环的落点，也让原来的 `user_behavior`、`hot_content` 两张闲置表第一次有真实用途（行为流水 + 常问作物统计） |
| **答案差评汇总** | 管理端新增「答案差评」（`/admin/bad-answers`）：把农户写的纠错说明汇总成**"最该先改的问题"** —— 按**同一个问法被标没帮助的次数**倒序（标点与空格差异算同一类），被反复指出（≥2 次）的标红条 + 「反复差评」徽标；另有**哪类方案差评最多**（带分母的差评率）与**差评明细**（点「看原答案」看当时答了什么）。侧栏「答案差评」旁的**橙色数字** = 名下范围内被标没帮助的条数 |
| **管理端 / 用户端** | 登录与注册都有**两种入口**：管理端（`/admin-page`）可以**添加用户端账号**（输入账号 + 密码）并**指定每个账号能种哪些作物、能用哪些土质**，也能把**别处的账号纳入管理**（自己注册的、或从其他管理端转入）；用户端建档时下拉里只有被授权的作物与土质，后端也会拦一道防绕过。角色存 `user.role`，归属存 `user.admin_id`，两类授权存 `user_crop_perm` / `user_soil_perm`（首次使用自动建好；原有账号在迁移时统一视为管理端） |
| **管理端的功能范围** | 管理端登录后的「功能」组只有：**工作台 / 今日待办 / 物候期提醒 / 历史记录**（首页卡片与之一致），另有「管理端」组三项：**用户端管理 / 反馈管理 / 答案差评**；拍照识病、四类处方、知识问答、经典图谱属于用户端，页面保留但不再陈列入口。管理端的「历史记录」是**名下用户端**的视角：**每条记录标明是谁问的**，可按用户端筛选，只能看自己名下（含自己），删除与清空仍只属于记录本人。管理端在「用户端管理」里还能**展开看每个账号的地块档案**（作物 / 面积 / 土质 / 播种日期 + 物候摘要），只读、且只能看自己名下的 |
| **一键启动** | 项目根目录 `一键启动.bat`：先做 7 项环境自检（依赖 / 配置 / Neo4j / MySQL / 资源 / 模型连通性），**顺手把 Neo4j 拉起来**，再启动服务并开浏览器；Neo4j 残留锁文件导致起不来时另有 `scripts/fix_neo4j_lock.py` 一键修复 |
| **拍照识病** | 上传作物照片 → 视觉大模型识别 → **回图谱对齐实体** → 直接输出防治方案。**原图不落盘**（只在内存压缩后送模型）；另存一张压缩缩略图随记录进「历史记录」，删记录时一并删除 |
| **方案导出** | 顾问生成的处方可一键导出 **Word / PDF**：含元信息、表格排版、知识溯源与页码，农户能打印带走 |
| **大模型** | 当前接入 **豆包（火山方舟）**，全部大模型调用收敛到 `core/llm_client.py` 一处；豆包 Seed 原生多模态，**图文共用一个模型**。协议走 OpenAI 兼容，换 DeepSeek / CMR / WorkBuddy / 本地 Ollama 只改配置；未配置时自动降级为图谱结构化输出，**功能不中断** |
| **可视化** | 经典图谱页：全关系类型 + 结构化属性 + 双向关联 + 搜索任意实体 |
| **溯源** | 每条结论附 `sources`（图谱三元组），可逐条复核，回答可解释 |

### 3. 大模型接入（当前：豆包 · 火山方舟）

系统统一走 **OpenAI 兼容协议**（`POST {base_url}/chat/completions`），
全项目**只有 `core/llm_client.py` 一处真正发请求**，其余模块都调它 ——
避免"三个地方各写一份、改一处漏两处"。

当前默认接入 **豆包（火山方舟 Volcengine Ark）**：

| 项 | 值 |
|---|---|
| 接口地址 | `https://ark.cn-beijing.volces.com/api/v3` |
| 模型名 | `doubao-seed-2-1-pro-260915`（也可填自建推理接入点 `ep-xxxx`） |
| API Key | 火山方舟控制台创建，形如 `ark-xxxxxxxx` |
| 视觉（拍照识病） | **复用同一个模型** —— 豆包 Seed 原生多模态，图文一个模型搞定 |

配置写在 `code/config_local.py`（优先级高于 `config.py`，不会被误提交）：

```python
LLM_PROVIDER = "doubao"
LLM_BASE_URL = "https://ark.cn-beijing.volces.com/api/v3"
LLM_API_KEY  = "ark-xxxxxxxx"
LLM_MODEL    = "doubao-seed-2-1-pro-260915"
```

#### 两个实测踩出来的关键点

**① 豆包必须关掉「思维链」，否则慢 6 倍还更容易失败**

豆包 Seed 系列默认先输出一大段思维链再给正文。同一个问题实测：

| 设置 | 耗时 | 正文 | completion_tokens |
|---|---|---|---|
| 默认（带思维链） | 27.9 s | 161 字 | 1115 |
| `thinking: disabled` | **4.4 s** | **191 字** | 128 |

短输出场景更夸张（`max_tokens=64`）：**60.2 秒 → 9.6 秒**。
原因是思维链把 `max_tokens` 全吃掉了，正文反而更短。

所以 `PROVIDERS["doubao"]` 里预置了 `params = {"thinking": {"type": "disabled"}}`，
`resolve_llm()` 会把 `params` 一并返回，`llm_client` 合并进请求体。
别的提供方不认识这个字段，所以做成「按提供方预置的附加请求参数」。
想恢复看思维链：`LLM_EXTRA_PARAMS = {"thinking": {"type": "enabled"}}`。

**② 必须重试，否则偶发慢请求会让整条链路降级**

连续 6 次同样的短请求，实测耗时分别是
`10.1 / 4.1 / 2.1 / 超时60s / 1.7 / 23.0` 秒 —— 服务端延迟波动很大。
只调一次的话，撞上慢请求就返回 None，整条链路降级成"图谱结构化输出"，
用户看到的是"有时候有润色、有时候没有"。所以：

- `LLM_TIMEOUT = 90`（原来 60 秒，实测会把慢请求直接判死）
- `LLM_RETRIES = 2`（失败等 1.5s / 3s 再试）
- 4xx 参数错误不重试（重试也没用，直接返回错误）

#### 怎么确认接对了（命令行 / 接口，界面不显示）

**界面有意不显示模型信息** —— 处方页、拍照识病页、问答页都不再出现
模型名与厂商名（例如 `doubao-seed-2-1-pro-260915`、`豆包（火山方舟）`），
结果旁边也不再挂「已润色 / 图谱结构化输出」这类标记。
理由：面向农户的界面上出现供应商型号只会造成困扰，也不便于演示时聚焦业务本身。

自检改走接口（都不回显密钥）：

| 接口 | 作用 |
|---|---|
| `GET /api/llm/status` | 看文本模型配置：provider / base_url / model / 超时 / 重试 / 是否关了思维链 |
| `POST /api/llm/test` | 真发一条最小请求，返回是否连通与模型回话 |
| `GET /api/vision/status` | 看视觉模型是否就绪、最大上传体积 |

命令行等价写法：

```bash
curl -s http://127.0.0.1:5000/api/llm/status
curl -s -X POST http://127.0.0.1:5000/api/llm/test
```

未配置时系统照常工作，答案自动走**图谱结构化输出**（只是界面上不再特意标注）。

- **分组**：`需要处理`（有高发风险，或 5 天内换期）/ `生长正常` / `未播种 · 已结束` / `今日已完成`

- **时间维度**：每张卡片带 `已种植 61 天（约 2 个月）` 与 `预计 12-18 收获（还剩 88 天）` 两个标签
- **深链**：点卡片任意位置跳 `/phenology-page?plot=<id>`，
  物候页读到参数后**自动弹出该地块的完整提醒**（时间轴、土质、农事、施肥、风险）；
  地块已被删除时静默跳过，不打断操作
- 顺带：`GET /api/plot/tasks?date=` 可查任意一天的完成记录 —— 留给后面的"完成率 / 农事台账"

### 历史记录与用户反馈：把"问过什么、答得好不好"留下来

农户用几天就会忘："上次那个药是哪一种来着？"——**历史记录**回答这个；
评委则会问："你凭什么说答得准？"——**用户反馈**回答这个。
两者是一件事的两头：**每一次问答都留痕，每一个答案都可被评价**。

#### 四张表，各管一段

| 表 | 存什么 | 来源 |
|---|---|---|
| `qa_history` | 问题 + 图谱答案 + 大模型答案 + 类型 + 知识溯源 | 每次提问 / 生成处方自动写入 |
| `qa_feedback` | 对某条记录的评价（`helpful` / `unhelpful`）+ 纠错说明 | 用户点「有帮助 / 没帮助」；**汇总见管理端「答案差评」页** |
| `user_behavior` | 行为流水（谁、何时、问了什么、命中哪个实体） | 提问与反馈时各写一条 |
| `hot_content` | 作物 / 病虫害被问次数 | 提问时按识别到的实体 +1 |

前三张表**沿用原项目 `database/hot_content.sql` 的字段设计**（`qa_history` 只追加了
`plan_type` / `plan_name` / `sources` 三个非破坏性字段，并对"已经导入过老 SQL 的库"
做了容错补列）。四张表都在**首次使用时自动创建**，不依赖手工执行 SQL。

> 这几张表在原项目里是"设计好了但从没被用过"的状态 —— 本次是它们第一次真正接上业务。

- **反馈回显**：卡片左侧色条与右上角标签显示"有帮助（绿）/ 没帮助（橙）"，
  纠错说明单独一行展示
- **清空历史**：二次确认后连同评价一起清掉

#### 管理端看到的是「谁问的」

管理端登录后打开同一页，看到的是**名下用户端**的记录：

```
历史记录   名下用户端提过的问题、生成过的方案 —— 每条都标明是谁问的

20 条记录 · 1 条有帮助 · 1 条没帮助 · 5 个用户端      常问： 小麦 6  小麦条锈病 3 …

[全部][知识问答][病虫害防治][水肥调控][农事管理][生产规划][基础问答]  [全部用户端 ▾]  [搜索框]

┌── 病虫害防治建议  [zhang001]  2026-09-23 10:32 ────────────────────┐
│ 小麦条锈病怎么防治                                                 │
│ [展开全文] [看溯源] [去这个功能]                       引用图谱 5 条 │
└────────────────────────────────────────────────────────────────────┘
```

- **可见范围 = 归属范围**：自己 + `admin_id` 指向自己的用户端（`app.py::_history_scope()`）。
  别的管理端名下的用户端，一条都看不到
- **每条标注用户**：卡片标题行多一枚蓝色账号徽标（用户端自己看时不会出现）
- **按用户端筛选**：筛选栏多一个下拉，选项由接口返回的 `scope_users` 填充
  （含还没问过问题的账号）；`?user=` 传了不在名下的值会被静默忽略，不构成越权入口
- **管理端只读**：删除与清空按钮在管理端视图里不出现；后端删除接口仍限本人（越权只会 404）
- 干活的是 `HistoryStore.list_multi()` / `stats_multi()` / `feedback_map_any()` 三个新方法
  （按一批用户名查询、每条带 `username`），原来的单人方法一个字段都没改

#### 导出成 Word / PDF

右上角两个按钮，导出的是**当前筛选下的记录**（类型 / 关键词 / 用户端都会带上）：

```
历史记录   我提过的问题、生成过的方案，以及我对答案的评价   [导出 Word] [导出 PDF] [清空历史]

文档内容 = 标题 + 元信息（导出时间 / 账号 / 条数 / 筛选条件 / 知识来源 / 含照片张数）
         + 每条记录：类型与时间（管理端还标着用户端）→ 问题 → **识病照片** → 答案
                    → 知识溯源 → 我的评价
```

- 复用处方那套 `core/exporter.py`（Word 用 python-docx、PDF 用 fpdf2，
  **都不需要装 Office / LibreOffice**）
- 文件在内存里生成、**不落盘**，直接以附件下载；名字形如 `我的历史记录_20260924.docx`
- 管理端导出的是**名下用户端**的记录，每条都标着是谁问的（`名下用户端历史记录_20260924.pdf`）
- 一次最多 5000 条（不走分页）；当前筛选没有记录时按钮置灰、接口返回「当前筛选下没有可导出的记录」
- **拍照识病带照片**：`qa_history.image` 存的缩略图 URL 经 `app.py::_history_photo_path()`
  翻译成站内绝对路径，在 markdown 里写成 `![图注](路径)`，`exporter` 渲染成居中图片 + 图注
  （Word 限宽 9.6cm、细高图按 11cm 高兜底，只给一边所以不会拉伸变形）
  —— 照片文件已随记录删除时降级为一行「（识病照片文件已不存在）」，不会让整份导出失败
  ⚠ 路径解析只认站内 `/static/` 开头，且 realpath 必须仍在 static 目录内（挡目录穿越）
- 顺手修了个小毛病：PDF 用的中文字体没有下标数字（CO₂ 之类）的字形，导出时会丢字并刷一堆字体警告
  —— 现在统一换成普通数字（`core/exporter.py::_plain`），处方导出也一并受益

#### 数据统计：四张图

页面顶部（概览与筛选栏之下）是四张统计图，**跟着筛选一起变**：

| 图 | 画什么 | 数据来源 |

| 柱状图 | 各类型记录数；**管理端换成"各用户端记录数"** | `/api/history/stats` 的 `by_type` / `by_user` |

#### 空态与异常态：三种"没数据"分别说人话

| 情形 | 页面表现 |
|---|---|
| 一条记录都没有 | 四张图统一显示「还没有记录，这里暂时没有数据」（`.ch-none`，早先柱状图是**一片空白**，看着像坏了）；概览归零且数字转灰；导出按钮置灰；列表给"去提一个问题"的引导 |
| 当前筛选筛不出东西 | 列表提示"没有符合条件的记录，换个筛选或关键词试试" |
| **MySQL 连不上** | 整块降级：列表说明原因、统计区与筛选栏**整个隐藏**、导出按钮置灰；**提问照常出答案**（少一个 `history_id`，反馈条不出现）；勾选/删除/反馈分别返回 503 而不是伪装成 404 |

> 降级提示里的原因**不是直接铺 pymysql 的原始异常** —— 原来会显示
> `(2003, "Can't connect to MySQL server on 'localhost' ([WinError 10061] 由于目标计算机积极拒绝，无法连接。)")`，
> 又长又吓人。`core/history_store.py::HistoryStore._error_text()` 把它压成一句人话
> （连不上 / 账号密码不对 / 没有这个库 / 没权限），**原始异常仍原样打到控制台日志**，排障不受影响。

#### 拍照识病也会留痕（`diagnose` 类型）

**为什么做**：农户最常问的一句话是"上次那个虫是什么来着？"。
拍照识病原本只在页面上出结果，关掉就没了 —— 现在识别完自动落一条历史，
连**照片缩略图**一起留下，翻历史就能看到"当时拍的到底是什么样"。

```
[拍照识病]  zhang001   2026-09-27 18:23
拍照识别：小麦
┌──────────┐
│ 麦穗缩略图 │  ← 点一下看大图
└──────────┘
照片里的作物：小麦
类别：健康（置信度：高）
可见症状：麦穗、茎秆呈正常青绿色，穗部排列规整，无病斑、虫损、黄化等异常
引用图谱关系 5 条                          [展开全文] [看溯源] [去这个功能] [删除]
```

- **问题取什么**：农户写了症状描述就用**原话**；没写就是「拍照识别：小麦」——
  列表里一眼能认出是"拍的那张"还是"打字问的"
- **两栏各存什么**：`kg_answer` 存照片识别结果 + 图谱对齐情况（作物 / 类别 / 置信度 /
  可见症状 / 对齐到的节点 / 引用了几条关系），`llm_answer` 存防治建议正文；
  卡片正文优先显示建议（与其他类型一致）
- **缩略图**：原图依旧不落盘（只在内存里压缩后送模型），
  另存一张**长边 480、约 40~60KB** 的小图到 `static/uploads/diag/<日期>/<随机名>.jpg`，
  库里 `qa_history.image` 只存 URL。文件名随机生成、不拼用户输入
- **文件生命周期**：删单条 / 清空历史时**连文件一起删**（`remove_thumb` 只允许删
  `static/uploads/` 里的东西，库里的值被人改过也删不到别处）；清空接口返回
  `images_removed` 说明顺手清掉了几张
- 两种模式都留痕：**只打字描述症状**（走图谱检索）也算一条，只是没有缩略图；
  描述里认不出实体时溯源为空 —— 但记录照样留下（不因为查不到就把这条丢掉）
- 拍照页在结果下方提示「已记入历史记录」并给回看入口；原文案"照片只在内存中处理、
  不保存到服务器"也一并改准了（现在是"原图不落盘 + 存一张缩略图"）
- 导出 Word / PDF 目前**不含照片**（导出模块只处理文字与表格）—— 需要的话再给 exporter 加插图支持

#### 反馈怎么用

答案下方（问答页与四类处方页都有）是一条常驻的反馈区：

```
这条回答对你有帮助吗？  你的评价会记进「历史记录」，用来改进这一类问题
[有帮助]  [没帮助]

（点"没帮助"后展开）
┌──────────────────────────────────────────────────────────────┐
│ 哪里不对？可以写下正确的说法，或补充作物的品种、地块情况（选填）│
└──────────────────────────────────────────────────────────────┘
[提交反馈]  提交后可在「历史记录」里看到这条评价
```

- 点「有帮助」**一步提交**；点「没帮助」先展开输入框，允许不写就提交
- 提交后按钮收起，显示「已记录：有帮助 / 没帮助」+ 一句感谢
- 界面**不出现模型名与厂商名**（与前面"界面不显示模型信息"的口径一致）
- 每条记录**只记一次评价**（唯一键 `history_id + username`，重复提交即覆盖）

#### 出答案的链路不受影响

三条入口（`/qa`、`/advisory`、`/api/advice`）在返回前统一调 `_record_history()`：

```python
result['history_id'] = _record_history(session['username'], question, result)
```

- 整段用 `try` 包住，**记不上历史绝不拦着用户看答案**，失败只打日志
- 前端拿到 `history_id` 才显示反馈区；拿不到（数据库不可用）就整块不显示
- MySQL 不可用时：历史页显示"需要数据库连接…不影响提问与生成"，
  查询返回空、写入返回 0 条，**没有任何一处抛异常**

#### 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/history?type=&q=&limit=` | 历史列表（含 stats 汇总与常问热度） |
| GET | `/api/history/<id>` | 单条详情 |
| DELETE | `/api/history/<id>` | 删除单条（连同它的评价与缩略图文件）；**先判归属**：别人的 404、库挂了 503 |
| POST | `/api/history/clear` | 清空本人全部记录（返回 `images_removed` 报告顺手删掉了几张缩略图） |
| POST | `/api/history/<id>/feedback` | 提交评价：`rating` + `comment`；同样先判归属 |
| GET | `/api/history/stats` | 图表数据：`by_type` / `by_user` / 近 14 天 `daily` / 问题高频词 `words` |
| GET | `/api/history/export` | 导出历史记录为 Word / PDF（`?fmt=docx\|pdf`，支持 `type` / `q` / `from` / `to` / `user` 筛选；**拍照识病的记录会嵌入照片**；无记录返回 400） |

> 所有接口都以 `session['username']` 为边界：**别人的记录读不到、评不了、也删不掉**
> —— 删除与反馈都是**先查归属、判 404，再动手**。
>
> ⚠ 删除这里踩过一个坑，值得写下来：`HistoryStore.delete()` 用的是
> `lastrowid is not None` 判成功，而一条都没删到时 lastrowid 是 **0**
> （`0 is not None` 为真）→ 「删别人的记录」原本会**返回 200 ok**。
> 数据本身是安全的（`WHERE` 里一直带着 `username`，影响 0 行），但**响应在骗人**。
> 现在改成与 `/api/econ/delete` 一致的写法：先 `get()` 判归属。
> 顺带把「库挂了」和「记录不存在」分开 —— `get()` 在数据库连不上时也返回 `None`，
> 一律当 404 会把"库挂了"说成"记录不存在"，提示词误导人
> （`app.py::_history_owned()` 返回 `ok` / `missing` / `down`，down 走 503）。

#### 意见反馈（页面，与上面的"答案评价"是两套东西）

| 页面 | 说明 |
|---|---|
| GET / POST `/feedback` | 用户端提意见，并在下方看到自己的反馈与回复 |
| GET `/admin/feedback` | 管理端看全部反馈、逐条回复；`?status=all\|pending\|replied` 筛选 |
| POST `/admin/feedback/reply` | 提交 / 修改回复（**回完跳回原来那个 tab**） |

- 侧栏「反馈管理」上的**红色未读数字 = 待回复条数**（`app.py::_inject_feedback_unread()`，
  context_processor 注入；**只有管理端才查库**，用户端页面一次都不查）
- **未读与"待回复"是同一个口径**，不额外加"已读"字段 —— 回一条就少一个，数字不会跟筛选打架
- ⚠ 判定统一走 `reply IS NULL OR reply = ''`，`FeedbackStore.all(status=)` 与 `stats()` **必须同口径**，
  否则会出现"列表 3 条、上面写 2 条待回复"这种对不上的情况
- `feedback` 表与历史评价表 `qa_feedback` 无关：前者是"给平台的意见"，后者是"对某条答案的评价"

#### 答案差评汇总：让「没帮助」不只是躺在库里

农户点「没帮助」时写的纠错说明，以前**只躺在 `qa_feedback` 里没人看**。管理端现在有一页
把这笔账算清楚 —— 这是"评价 → 改进"闭环真正落上的地方。

| 页面 / 接口 | 说明 |
|---|---|
| GET `/admin/bad-answers` | 差评汇总页；`?days=30\|90\|365\|all`（默认 all）、`?type=` 方案类型 |
| GET `/api/admin/bad-answer/<id>` | 取某条记录的原问答（「看原答案」弹层用；越界 id 返回 404） |

页面分四块：

1. **四个数字**：被评价条数 / 标了「没帮助」条数 / 差评率 / 其中写了纠错说明的条数
2. **最该先改的问题**（`by_question`）—— **同一个问法被标没帮助的次数**倒序，
   被反复指出（≥2 次）的左侧标红条 + 「反复差评」徽标，问题下面直接列农户的原话
3. **哪类方案差评最多**（`by_type`）—— 横向条 + 「N / M 条 差评率」
4. **差评明细**（`items`）—— 逐条列出，带「看原答案」弹层（异步拉全文）

三个必须说清的实现口径：

- ⚠ **"哪条答案被标没帮助最多"不能按 `history_id` 聚**：`qa_feedback` 的唯一键是
  `(history_id, username)`，一条记录最多一条评价，按 id 分组 count 恒为 1，永远排不出"最多"。
  真正该聚的是**"同一个问题"** —— 所以用 `_norm_q()`（**剔除标点与空格**后比对）聚类，
  「小麦条锈病怎么防治？」「小麦条锈病 怎么防治」「小麦条锈病怎么防治！！！」算同一类
- ⚠ **差评率必须带分母**：只看差评绝对数会被"问得多的类型"带偏，
  所以 `by_type` 给的是 `差评数 / 该类型被评价数`；分母 < 3 的标一句「样本少」
- ⚠ 侧栏「答案差评」的**橙色数字**（与"待回复"的红色区分）来自
  `HistoryStore.count_unhelpful(scope)` —— **单独一条轻量 COUNT**，
  不要复用 `feedback_review()`（后者会把问题与纠错说明整批拉出来，而侧栏每渲染一页都跑一次）
- 统计范围走 `_history_scope()`：管理端 = 自己 + **名下**用户端；用户端**进不去这一页**（渲染拒绝页）
- 「看原答案」走 `HistoryStore.get_in(scope, id)`，**越界的 id 查不到**，
  返回 404 而不是 403（不暴露"这条存在但你看不了"）

### 农作物经济效益测算：种啥更划算

农户选种时要算的是三笔账：**能卖多少、要投多少、最后剩多少**。
`/econ-page` 把这三笔账做成一张表单 + 一张对比榜：

```
经济效益测算   填一组投入产出，自动算收益 —— 几个作物摆在一起，种啥更划算一目了然

2 个测算方案 · 玉米（710 元/亩）最划算 · 605 元/亩 平均净收益 · 0 个方案亏损

┌ 新增一个测算 ────────────────────┐ ┌ 收益对比 ──────────────────────────┐
│ 作物   [玉米 ▾]（图谱全部作物）  │ │ ① 玉米     710 元/亩               │
│ 面积 [3.5]亩 · 预期亩产 [600]公斤│ │   亩收入 1320 · 亩成本 610 · 2.16  │
│ 收购价 [2.20] 元/公斤            │ │ ② 小麦     500 元/亩               │
│ 投入成本（元/亩，留空按 0 算）   │ │   亩收入 1170 · 亩成本 670 · 1.75  │
│ 种子种苗 化肥 农药 机械作业      │ │                                    │
│ 人工 灌溉 其他                   │ │   ▂▄▆ 总收入/总成本/总净收益柱状图 │
│ 备注 ______________              │ └────────────────────────────────────┘
│ [保存并加入对比] [清空重填]      │
└──────────────────────────────────┘
```

- **算法**（写在 `core/econ_store.py::compute()`，纯函数，前端只负责展示）：
  亩收入 = 亩产 × 收购价；亩成本 = 七项之和；净收益 = 收入 − 成本；
  总面积只做等比例放大；投入产出比 = 亩收入 ÷ 亩成本
- **两个保本数最实用**：`保本收购价 = 亩成本 ÷ 亩产`（"价格跌到 1.02 元/公斤就白干"）、
  `保本亩产 = 亩成本 ÷ 收购价`（"亩产低于 277 公斤就亏"）
- **排序用亩均净收益**而不是总额 —— 地块大小不同也公平；柱状图同时给
  总收入 / 总成本 / 总净收益三个系列，一眼看出"看着卖得多、其实没剩多少"的作物
- 卡片列全明细（亩收入 / 亩成本 / 总收入 / 总成本 / 投入产出比 / 保本价 / 成本构成），
  亏本的方案左侧色条转红并标「会亏」
- **作物清单取图谱全集**：算收益就是为了决策比较，只给"我被授权能种的那几种"就失去意义了
  —— 与知识问答、四类处方同一个口径（这三处都不受授权限制）
- 数据落 `crop_econ` 表（首次使用自动创建），按账号隔离：自己的能看能改能删，
  别人的读不到也删不掉（越权 404）
- 面积可以留空（按 1 亩估），页面上会标出来，免得把"1 亩的收益"当成整块地的收益

### 管理端 / 用户端：谁能种什么、能用什么地，由管理端说了算

同一套系统，两种身份：

| 身份 | 能做什么 | 数据边界 |
|---|---|---|
| **管理端**（`admin`） | 添加用户端账号（输入账号 + 密码）、指定每个账号**能种哪些作物、能用哪些土质**、纳入/转入别处的账号、重置密码、解除管理、删除账号 | 只能操作**自己名下**的用户端 |
| **用户端**（`user`） | 拍照识病、物候期建档、四类处方、知识问答、历史记录、经济效益测算 —— 即原来的全部功能 | 建档时只能选被授权的作物与土质（**问答 / 处方 / 经济效益测算不受此限**，决策要能自由比较） |

> **管理端的菜单只留四个功能**：今日待办、物候期提醒、历史记录、用户端管理。
> 拍照识病、知识问答、四类处方与经典图谱不再出现在管理端的菜单与首页卡片里
> （页面本身保留，直接输地址仍可访问）。这样管理端进去就是"管人 + 看情况"两件事，
> 不用和自己名下的用户端抢同一套种地功能。
>
> 管理端的「历史记录」也顺带换成了**名下用户端**的视角 —— 每张卡片标着是谁问的，
> 还能按用户端筛一遍，具体见「历史记录与用户反馈」那一节。

> 管理端点开看到的内容，跟农户自己看到的一字不差；以后改样式、改详情只改这一处。

|---|---|---|
| 作物 | `GET /api/phenology/crops` 只返回授权作物 | `POST /api/plot/save` 拦下未授权的作物 |
| 土质 | `GET /api/soil/list` 只返回授权土质 | `POST /api/plot/save` 拦下未授权的土质 |

「添加地块」和「快速推算」两个下拉都受影响。被拦时的提示：

> 你的账号未被授权种植「水稻」。当前可种：小麦、玉米。如需增加，请联系管理员在你的账号里添加。
>
> 你的账号未授权使用土质「砖红壤」。当前可用：壤土、黑土。如需增加，请联系管理员在你的账号里添加。

受限账号打开物候期页时，顶部会有一条蓝底提示（横跨整行）：

> 本账号的可用范围由管理员设定：作物 **小麦、玉米**（2 种）　·　土质 **壤土、黑土**（2 种）　
> 如需增加，请联系管理员在「管理端 · 用户端管理」里添加

> **边界说明**：限制作用在**物候期建档**（"我种了什么、我家的地是什么土"这两件事的落点）。
> 四类处方与知识问答的作物/土质下拉**不做限制** —— 那是查询与学习工具，
> 限定反而会让功能显得残缺（农户也可能想查别的作物、别的土壤怎么处理）。

> 概览条只报**与我有关的三个数**（我管理的用户端 / 作物有限制 / 土质有限制）——
> 系统账号总数、管理端数量属于运维信息，界面上不出现。
> 接口 `GET /api/admin/overview` 返回的 `stats` 里仍然带着 `total_users` 与
> `total_admins` 两个字段（供自检与外部集成用，只是不再展示）。

#### 权限是怎么保护的

- 页面：`/admin-page` 对用户端返回 `admin_denied.html`（说明 + 回工作台 / 切换账号）
- 接口：`/api/admin/*` 统一走 `_admin_guard()`，用户端调用一律 403
- 归属：所有写操作先经 `_check_my_user()` 校验"这个账号确实在我名下" ——
  换个管理端来改、来删都会得到「不在你名下，无权操作」；管理端账号本身也不允许被这样管理

#### 用到的表

| 表 | 变化 |
|---|---|
| `user` | 补三列：`role`（admin/user）、`admin_id`（归属的管理端 id）、`create_time` |
| `user_crop_perm` | 新建：`username + crop` 唯一，记"允许这个账号种什么" |
| `user_soil_perm` | 新建：`username + soil` 唯一，记"允许这个账号用什么土" |
| `user_plot` | 补一列 `ph`（decimal，农户手填的土壤 pH，选填）—— 老库由 `PlotStore.MIGRATE` 自动 `ALTER` 补上（靠错误码 1060 判定"已经有了"） |

后两张表**结构完全一样**，读写共用一套 `perms_of / set_perms / _replace_perms`
（`kind` 取 `crops` 或 `soils`），所以再加一类授权只需要往 `PERM_TABLES` 里加一行。

三处都**首次使用时自动完成**（`core/user_admin.py::ensure_schema()`，应用启动即执行），
不依赖手工执行 SQL。**补 `role` 列的那一次**会把已有账号统一设为管理端，
而这一动作只在列不存在时发生 —— 之后再启动不会把用户端又改回管理端。

> MySQL 不可用时整块安全降级：管理端页显示"数据库不可用"，
> 接口返回失败但不抛异常，**用户端照常提问、看图、建档**。

#### 作物清单读不到时，页面会说清原因

作物下拉的数据来自图谱（Neo4j），读不到时页面不会只留一句"加载失败"：

```
作物列表加载失败：知识图谱（Neo4j）未连接：Driver closed
作物清单读自知识图谱（Neo4j），确认图谱服务在运行、图谱数据完好后，点 重新加载
```

- `GET /api/admin/crops` 失败时返回 `ok=false` + **中文原因**，而不是空数组
- 页面给一个「**重新加载**」链接（不用刷整页）
- 用户列表、重置密码、解除管理**不受影响** —— 作物清单与用户列表是各拉各的，互不阻塞
- 物候期页的作物下拉同样会把原因显示在选项里（例如
  「读取失败：知识图谱（Neo4j）未连接…」），而不是含糊的"暂无数据"

#### 一个隐蔽的连接问题（已修）

原来 `/logout` 里会关闭 RAG / 顾问的**全局连接** —— 但它们是进程级共享单例：
**任何一个账号登出，就把所有人的连接都拆了**。更麻烦的是物候引擎还抱着顾问的连接
（`PhenologyEngine(get_advisor().conn)`），于是**登出一次之后**：

| 现象 | 原因 |
|---|---|
| 管理端"能种什么"是空的（作物列表加载失败） | 读作物要经过物候引擎 |
| 物候期页作物下拉"暂无数据" | 同上 |
| 四类处方、知识问答也报错 | 顾问/RAG 连接同样被关 |

只能重启服务才能恢复。现在做了两件事：

1. **`/logout` 只清会话，不再关闭共享连接**（连接常驻复用，进程退出时回收）
2. 三个单例（顾问 / 物候 / RAG）都加了**自愈**：`_conn_alive()` 先探一下，
   连接不可用就自动重建 —— 以后就算别处误关，也不会整站瘫掉

> 顺带说明：单例自愈是有代价的（重建顾问要重新加载实体），所以只在**真的连不上**时才走这条路。

### 全局左侧导航

所有登录后的页面都共用 `templates/_nav.html` —— 页面只需在 `<body>` 开头加一行：

```jinja
{% include '_nav.html' %}
```

它自带样式与结构，因此**不用改各页已有的布局代码**：

- **固定左侧栏**（226px，宽屏 246px），含品牌区、功能分组、底部用户信息
- **当前页自动高亮**：靠 `request.path` 前缀判断（浅蓝底 + 左侧蓝条 + 文字变蓝），无需每个页面传参数
- **三个分组**：`功能`（工作台、今日待办、拍照识病、物候期提醒、知识问答、历史记录、**经济效益测算**）+ `决策处方`（病虫害防治建议、水肥调控处方、农事管理方案、生产规划报告）+ `知识图谱`（经典图谱），今日待办、拍照识病与物候期提醒带"推荐"标记，经济效益测算带"新"标记
- **第四个分组 `管理端` 只对管理端账号出现**（内含「用户端管理」）——
  两种身份看到的菜单本就不同；侧栏底部的用户信息栏还带一枚**角色徽标**
  （管理端蓝 / 用户端灰），随时知道自己在哪一端
- **管理端的菜单只剩四个功能**：今日待办、物候期提醒、历史记录、用户端管理
  （外加"工作台"这一个回首页的导航项）。拍照识病、知识问答、四类处方与经典图谱是
  **用户端**的活儿，对管理端不输出入口 —— 实现上只是用 `{% if not _admin %}` 把这几个
  `nav-item` 包起来，**路由与页面照旧可用**，直接输地址仍能打开，只是菜单里不再陈列。
  首页（工作台）的四张功能卡与菜单保持一致。以后想让管理端也能用某个功能，
  去掉它外面的那个 `{% if %}` 就行
- 各页顶部原本的"返回工作台"等重复跳转链接已移除，只保留页面标题与说明
- `body` 的内边距由片段统一处理，各页面无需适配

#### 例外：首页（工作台）不显示侧栏

工作台本身就是**一张功能卡片清单**，再挂一条"功能表"是重复的，还白占 226px 宽度。
所以 `_nav.html` 开头有一张例外名单：

```jinja
{% set _hide_nav = ['/success'] %}
{% if _p not in _hide_nav %}
```

命中时**整个片段（样式 + 顶栏 + 抽屉 + 脚本）都不输出**，于是：

- 首页回到**整幅居中**布局（`.page` 放宽到 1180px，9 张卡片刚好 3×3 排满）
- `body` 的 226px 左侧留白随片段一起消失，不留一块空白
- **不需要在 `success.html` 里写任何条件** —— 页面照旧只写 `{% include '_nav.html' %}`，
  显隐逻辑全在片段内部，以后想给别的页面也关掉，往名单里加路径即可
- 因为连脚本也没输出，首页不存在"指向不存在的 DOM"的报错
- **退出登录挪到了欢迎区右上角**（原来在侧栏底部），否则首页没有出口

> 手机上同理：首页没有左上角收纳按钮 —— 它本来就是菜单页，点卡片即可进入功能，
> 进去之后收纳栏才出现，随时能换页。

#### 手机端：左上角收纳栏（抽屉式）

窄屏（≤980px）时侧栏自动收起，**左上角一个收纳按钮**随时开合：

- 顶栏固定 54px：左侧收纳按钮 + 系统名 + 右侧用户头像
- 点按钮从左侧滑出抽屉（264px，竖向布局，与桌面端一致），背后加深色遮罩
- **四种收起方式**：再点按钮 / 点遮罩 / 点抽屉右上角 × / 按 Esc；**点任一功能项也会自动收起**
- 抽屉打开时锁定背景滚动，避免手指滑到背后内容
- 窗口拉宽回桌面尺寸时自动复位，不会残留遮罩
- 窄屏下弹层类元素（物候期详情）层级高于顶栏，不会被遮挡

> 之前是"顶部横向导航条"，九个功能横排需要左右滑动才能看全，手机上很难发现。
> 改成收纳栏后，顶栏只用一行，功能列表展开即见全貌。

### 流式输出：不用再盯着白屏等二十秒

大模型是逐字生成的，但接口原来是"整篇写完再一次性返回"——实测一次问答
**平均 20 秒全程白屏**（老接口 `/advisory` 实测 17~18 秒）。现在改成 SSE：
**检索一结束就把类型 / 实体 / 溯源推给前端，正文逐段到达**。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/qa/stream` | 知识问答页：`question` + `mode`(advisor\|basic) |
| POST | `/api/advice?stream=1` | 四类处方页（body 里带 `stream: 1` 等效） |

事件顺序（每帧一行 `data: {json}`）：

```
meta     类型 / 识别实体 / 溯源 / 追问建议      ← 通常 0.5~4 秒就到
delta    大模型正文片段，0~N 条
history  本次问答的历史记录 id（数据库不可用则没有这条）
done     answer / llm_used / structured / ...  与老接口返回完全一致
error    生成失败（前端会自动退回一次性接口再试）
```

**实测**（浏览器里每 0.4 秒采一次答案字数）：

| 场景 | 首字出现 | 全部写完 | 感受 |
|---|---|---|---|
| 知识问答（advisor） | **2.5~2.9 秒** | 15~19 秒 | 白屏从 20 秒降到 ~3 秒 |
| 知识问答（basic 图谱问答） | 4.2 秒 | 20.5 秒 | 同上 |
| 四类处方页 | **0.4~2.0 秒** | 18~33 秒 | 同上 |

实现要点（三条都是踩出来的）：

- `core/llm_client.py::chat_stream()` 是**唯一**的流式入口，`requests` 用 `stream=True`
  逐行解析 `data:`。⚠ **重试只在还没吐出任何片段时发生** —— 一旦开始往外吐字，
  中途断流就只报失败、绝不重发，否则前端会看到"同一段话说两遍"
- 检索与非流式共用 `_prepare()`、提示词共用 `_refine_prompt()` / `_compose_prompt()`：
  两条链路必须算出同一份溯源，否则流式与非流式的答案会对不上
- `app.py::_sse_response()` 用**后台线程 + 队列**跑生成器，主线程每 8 秒发一次 `: ping` 心跳
  （首字要等好几秒，中间不发数据容易被中间层掐断）；**历史落库回到主线程做** ——
  子线程没有请求上下文，读不到 `session`
- 前端 `static/qa_stream.js`（两个页面共用）：`fetch` 读 `ReadableStream` → 按 `\n\n` 切帧
  → JSON 解析。Markdown 每 90 毫秒重渲染一次（节流），配合 `md2html(md, partial)` 的容错
  （补上没写完的 `**`、丢掉半截表格行），中间态才不会闪
- **降级链完整**：服务端没给 SSE / 流式一个字都没收到 → 自动退回老接口
  `/qa`、`/advisory`、`/api/advice`；后端中途断流且只吐了一两句 → 答案退回图谱原文
  （`llm_used=false`），由 `done` 一次性覆盖。**老接口保留不动**，小程序端不受影响

### 物候期自动提醒（今天该干什么）

**这是"从查得到到用得上"的关键一跳**：问答是用户主动问，提醒是系统主动告诉。

原理很简单但完全靠图谱数据支撑 —— 每个作物的生育期节点上都带
`阶段序号 / 历时天数 / 起始日 / 结束日`（均为播种后天数），所以只要知道**播种日期**，
就能算出今天落在哪个阶段、还剩几天、下一阶段什么时候来。

```python
from core.phenology import PhenologyEngine
eng = PhenologyEngine(conn)
r = eng.reminder("小麦", "2026-03-03")     # 作物 + 播种日期
print(r["message"])
# 播种后第 201 天，处于【灌浆期】第 22/36 天，还有 15 天进入【成熟收获期】
```

一次调用返回：

| 字段 | 内容 |
|---|---|
| `stage` / `stage_day` / `stage_left` | 当前阶段、阶段内第几天、还剩几天 |
| `overall_percent` | 全生育期进度百分比（用于进度条） |
| `todo` | **当前阶段该做的农事**（来自 `生育期-[栽培要点]->农事操作`） |
| `fertilize` | 施肥要点：按阶段判定重点（基肥 / 促根提苗 / 氮钾并重 / 稳氮增钾 / 磷钾为主 / 停止施肥）+ 匹配的肥料与施用方式 |
| `risks` | 当期病虫害与草害风险（用病虫害的 `常发时期` 与当前阶段做**区间匹配**），按危害等级排序，附防治措施 |
| `next_soon` / `next_risks` | **提前 5 天预警**"即将进入 XX 期"，并列出下一阶段要防的病虫害 |
| `elapsed_days` / `elapsed_text` | **已种植多久**：`61` / `61 天（约 2 个月）` |
| `harvest_date` / `harvest_md` / `days_to_harvest` | **预计收获日**与剩余天数：`2026-12-18` / `12-18` / `88` |

边界情况都已处理：还没播种（提示距播种天数）、已过收获期（提示准备下一茬）、
无生育期数据（友好提示换作物）、日期格式错误（返回 400 与中文说明）。

### 「已经种了多久」：补录地块也不吃亏

**动机**：农户往往是种下去一段时间之后才来录入地块的，不一定记得准确播种日期。
所以这块做了两件事：

**① 算出并突出显示"已种植多久"**（不是藏在句子里的"播种后第 N 天"）：

- `elapsed_days` = 播种当日起算的天数（播种当天记为第 1 天，与 `day_no` 同口径）
- `elapsed_text` 说成人话 —— 小数量级直接给天数，超过一个月再附约数量级：

  | 天数 | 显示 |
  |---|---|
  | 28 | `28 天` |
  | 45 | `45 天（约 1.5 个月）` |
  | 61 | `61 天（约 2 个月）` |
  | 364 | `364 天（约 12 个月）` |
  | 400 | `400 天（约 1.1 年）` |

  量级越大越不显示小数（`61 天` 说"约 2 个月"比"约 2.03 个月"好读）。

**② 顺带给出"预计什么时候能收"**：

- `harvest_date` = 播种日 + (全生育期天数 - 1) —— 因为播种当天记为第 1 天，
  直接加 `total_days` 会多算一天
- `days_to_harvest` = 全生育期天数 - 已种植天数，生长期为正、已过收获期为负

**③ 填表时支持"按已种植天数反推日期"**：两个表单的播种日期下面都有一行
「记不清日期？填已种植天数」，输入 30 就自动把上面的日期框填成 `今天 - 29 天`。
**结果直接体现在日期框里**，不再额外显示一行"→ 日期"（日期框本身已经给出反馈，多一行反而啰嗦）。
用的是同一套口径（`播种日 = 今天 - (天数 - 1)`），所以**填 30 天，系统就显示已种植 30 天**，
不会差一天。

展示位置：

| 位置 | 显示 |
|---|---|
| 地块九宫格卡片 | `已种植 61 天（约 2 个月）` + `预计 12-18 收获` 两个标签 |
| 详情弹层头部 | 一行标出 `已种植 61 天（约 2 个月）` 与 `预计 2026-12-18 收获（还剩 88 天）` |
| 今日待办页卡片 | 同上两个标签，与其他状态并列 |

> 尚未播种的不显示已种植时长，只显示距播种天数。

（农事、施肥、病虫害风险），并配一张**该阶段的植株示意图**：

- 当前阶段标「当前阶段」；点看别的阶段时，会提示"这是**已经过** / **还没到**的阶段，供提前规划参考"
- 选中的时段加绿色描边，右上角出现「回到当前阶段」按钮
- 接口 `POST /api/phenology/stage`（参数 `crop` / `index` / `sow_date` / `soil` / `ph`）按需加载，不浪费请求

**配图怎么来的**：图谱里各作物对生育期的叫法共 **287 个阶段名**（64 个唯一短名），
逐个配图不现实。所以归并成 **12 个通用阶段类型**，每个类型配一张**实拍照片**
（`static/stages/<图标>.jpg`，600×600、约 50~120 KB）；`scripts/gen_stage_icons.py`
按同一套类型**参数化生成的 SVG 示意图**（`static/stages/*.svg`，单张约 1 KB）保留作**兜底**：
页面优先加载 `.jpg`，某张照片缺失时 `onerror` 自动回落到同名 `.svg`（不会出现破图）。

> 想换成自己拍的田间照片：直接覆盖 `static/stages/<图标>.jpg` 即可（正面方形构图最好，
> 页面用 `object-fit: cover` 裁进 122×106 的框，不会变形）。12 个图标与阶段关键词的对应关系见下表：

| 图标 | 覆盖阶段关键词 |
|---|---|
| `sowing` | 播种、出苗、萌芽、直播 |
| `seedling` | 育苗、移栽、定植、缓苗、苗期、幼苗、幼龄 |
| `tillering` | 分蘖、分枝、发棵 |
| `jointing` | 拔节、伸蔓、蕾薹、抽梢 |
| `booting` | 孕穗、现蕾、蕾期、花芽分化 |
| `flowering` | 抽穗、开花、花铃 |
| `filling` | 灌浆、结荚、鼓粒、角果、淀粉/糖分积累 |
| `enlarging` | 果实膨大、幼果、浆果、块根块茎、根部药用部位 |
| `maturing` | 成熟、收获、采收、采摘、吐絮、转色、采挖 |
| `vegetative` | 莲座、叶片生长、营养/生殖生长、旺盛 |

规则**有序匹配**（具体的在前、泛化的兜底），实测 **287 个阶段名 100% 命中**。

随主题配色可调、离线可用，且改一个参数就能重新生成全部。

### 土质联动（同一作物，不同地要不同管法）

地块里选了土质后，提醒会多出一节「土质与土壤管理」，做三件事：

**① 核对适配性。** 查图谱里该作物的 `适宜土壤`，给出匹配结论：

- 匹配 → 绿色提示"「潮土」是 小麦 的适宜土壤之一，匹配良好"
- 不匹配 → 黄色提示"图谱中 小麦 的适宜土壤为：砂姜黑土、黑土、潮土、褐土……
  当前选择「红壤」，建议关注下面的水肥调整要点"（只提示、不否定农户的选择）

**② 按土壤属性给差异化管理要点。** 数据来自土壤节点的 `质地 / 肥力水平 / 保水性`：

| 土壤特征 | 管理调整 |
|---|---|
| 砂质、砾石、风沙 | 追肥「少量多次」、单次减量 20%~30%；小水勤灌防淋失；增施有机肥 |
| 黏质、重壤 | 开沟排水防渍；施肥可集中但忌一次过量；深耕改善通透性 |
| 肥力偏低 | 增施有机肥 + 测土配方，避免盲目加化肥 |
| 保水性差 / 强 | 提高灌溉频次 / 注意排水防渍 |
| 偏碱（pH>7.5） | 易缺铁锌硼，叶面补微肥；可施石膏或生理酸性肥改良 |
| 偏酸（pH<6.5） | 可施石灰调酸（每亩 50~100 kg）；适合喜酸作物 |

**酸碱度只看农户自己填的值，不显示图谱值**（`user_plot.ph`，选填，0~14）：

- 图谱里土壤节点的 `酸碱度` 只是"这个土类大概什么范围"（如壤土 `pH5.5-6.5`），
  跟自家地块实测出来的值常常对不上 —— 摆两个数只会让农户困惑，所以页面上**不再显示**，
  土质表格里的「酸碱度」列也一并去掉（现在是 质地 / 肥力 / 保水性 / 主要分布 四列），
  土质下拉里也只留质地与常用改良剂
- 改成在「添加 / 更新地块」和「快速推算」里各给一个 **`土壤 pH`（选填）** 输入；
  填了才按 5.5 / 6.5 / 7.5 三档给调酸或调碱建议，没填就不显示也不给建议
  （宁可不说话，也不拿一个跟自家地块对不上的值给建议）
- 卡片与详情头部会显示 `pH 6.5` 这样的标签；**没选土质也会显示** —— pH 是地块自己的属性
- 手填数字最容易越界（把 6.5 打成 65），所以 `core/plot_store.py::parse_ph()`
  在**后端**拦一道：非数字 / 超出 0~14 一律拒绝并给中文提示，且不会把原值改坏

**③ 施肥建议随土质改写。** 举个例子，同样是灌浆期追肥：

> 选「潮土」（壤质）→ 该土壤质地与保水性适中，按上面的施肥要点执行即可
> 选「风沙土」（砂质）→ 该土壤质地偏砂（砂质）：保肥差，基肥建议分次施入，
> 追肥「少量多次」，单次用量减 20%~30%、间隔缩短 3~5 天

### 拍照识别病虫害

#### 前提：得有一个"看得见"的模型 —— 现在用豆包一个搞定

**纯文本模型把图片喂进去是看不见的**（例如 `deepseek-chat`）。
当前用的 **`doubao-seed-2-1-pro` 本身原生多模态**，所以 `LLM_VISION_*` 三项**留空也能用** ——
`resolve_vision()` 会自动复用主模型（判断依据是模型名命中 `VISION_HINTS`，豆包在列）。

如果以后换成纯文本主模型，就要单独配一个视觉模型（三项写在 `config_local.py`）：

```python
LLM_VISION_BASE_URL = "https://dashscope.aliyuncs.com/compatible-mode/v1"
LLM_VISION_API_KEY  = "sk-xxxxxxxx"
LLM_VISION_MODEL    = "qwen-vl-max"
```

| 可选服务 | Base URL | 模型名 |
|---|---|---|
| 豆包（原生多模态，复用主模型即可） | `https://ark.cn-beijing.volces.com/api/v3` | `doubao-seed-2-1-pro-260915` |
| 通义千问 VL（阿里百炼） | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-vl-max` |
| 智谱 GLM-4V | `https://open.bigmodel.cn/api/paas/v4` | `glm-4v-plus` |
| OpenAI | `https://api.openai.com/v1` | `gpt-4o` |

未配置时**不会假装识别成功**：识别请求会返回明确失败原因（显示在结果区），
用户仍可改用「填写症状描述」拿图谱给防治建议。
（界面上不显示视觉模型的型号与就绪状态，自检走 `GET /api/vision/status`。）

#### 关键设计：识别结果要回图谱对齐，不能直接采信

大模型给出的病名常常不规范。实测中模型返回的是简称「**条锈**」——
这个名字直接拿去查图谱是查不到的，也就拿不到任何防治数据。所以系统会把识别结果
送回图谱做**实体对齐**（多轮检索 + 相似度打分：完全一致 100 > 包含 60+ > 最长公共子串×8）：

| 模型输出 | 对齐到图谱实体 | 说明 |
|---|---|---|
| 条锈 | 小麦条锈病 | 简称补全 |
| 稻瘟 | 稻瘟病 | 简称补全 |
| 锈病 | 锈病 | 精确命中 |
| 看麦娘 | 看麦娘（杂草） | 跨类别命中 |
| 完全不存在的东西 | 未匹配 | 如实返回候选，不硬凑 |

只有对齐到图谱节点，才能顺带给出危害部位、常发时期、危害等级、防治措施（含安全间隔期）
—— 这才是"识别完能照着治"，而不是"识别完还得自己查"。

#### 处理链路

1. **压缩**：图片在内存中长边压到 1280px、JPEG q85、转 base64 data URL。
   实测 2400×1600 的 232 KB 图压到 base64 后 74 KB，显著省 token。
   手机竖拍照片会按 EXIF 自动转正。
2. **识别**：调视觉模型，提示词要求严格 JSON 输出
   （作物 / 病虫害 / 类别 / 可见依据 / 置信度 / 备选），并要求"看不出就如实说不确定"。
3. **容错解析**：模型常把 JSON 包在 ```` ```json ```` 代码块里，做了提取与常见尾逗号修复。
4. **图谱对齐**：见上表。
5. **出方案**：用对齐后的实体调 `AgriAdvisor.pest_advice()`，生成绿色防控排序的防治建议。

#### 隐私与安全

- **原图不落盘**：只在内存中处理、压缩后送模型，服务器不留存原图；
  只额外存一张**压缩缩略图**（`static/uploads/diag/<日期>/`，长边 480、约 40~60KB）供「历史记录」回看，
  删单条 / 清空历史时文件会一起删掉（`core/vision.py::save_thumb` / `remove_thumb`）
- 单张上限 8 MB（超过返回 413 并给出提示），支持 JPG / PNG / WEBP，也支持直接粘贴截图
- 结果页固定展示免责声明："识别结果由 AI 根据照片推断，仅供田间参考；重大病虫害请以当地植保部门鉴定为准"

HTTP 接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/diagnose-page` | 拍照识病页 |
| GET | `/api/vision/status` | 视觉模型接入状态（不含密钥） |
| POST | `/api/diagnose` | 识别接口，表单字段 `image`（文件）/ `crop` / `description`；识别完**自动落一条历史**（`plan_type=diagnose`）并返回 `history_id` 与缩略图 `image` |

> `image` 为空时会自动切换到「文字描述症状」模式，走图谱检索出防治建议。
> 两种模式都会落历史：问题取农户写的症状描述（没写就是"拍照识别：作物名"），
> 「知识图谱答案」一栏记的是照片识别结果与图谱对齐情况（作物 / 类别 / 置信度 / 可见症状 / 对齐到的节点），
> 正文是防治建议。缩略图路径存在 `qa_history.image`，删记录 / 清空历史时会连文件一起删。

### 方案导出（Word / PDF）

顾问页生成方案后，右上角会出现「导出 Word」「导出 PDF」两个按钮 —— 农户能把处方**打印带走**，
这是"从查得到到用得上"的最后一公里。

实现要点：

- **Word**：`python-docx` 生成真正的 `.docx`（不是 HTML 改名），Word/WPS 打开无格式警告；
  表格用 `Table Grid` 样式，标题走主题蓝
- **PDF**：`fpdf2` 生成，**嵌入系统中文字体**（正文微软雅黑 `msyh.ttc`、标题用雅黑粗体 `msyhbd.ttc`），
  所以中文不会乱码也不会变方框；找不到系统字体时会明确报错而不是产出乱码 PDF
- 两者**共用同一套 Markdown 解析**，支持：一/二级标题、引用、无序/有序列表、`**加粗**`、以及**表格**
  （方案中的生育期时间轴、适种作物表都是表格，必须支持）
- 文档头自动带元信息（适用作物 / 生成时间 / 生成账号 / 知识来源），
  文末附**知识溯源清单**与免责说明，PDF 每页有页码
- 文件在**内存中生成后直接返回**，不落盘；文件名形如 `农事管理方案_20260921.docx`

踩过的坑：fpdf2 的 `multi_cell()` 默认把光标停在**行尾**（`XPos.RIGHT`），
若不加 `new_x="LMARGIN", new_y="NEXT"`，下一个块会因起始 x 已在右边界而报
`Not enough horizontal space to render a single character`。

HTTP 接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/export/docx` | 导出 Word，参数 `title` / `markdown` / `sources` / `crop` |
| POST | `/api/export/pdf` | 导出 PDF，参数同上 |

## 六、对照赛题评审点

| 评审维度 | 本项目对应设计 |
|---|---|
| **回答的专业性** | 事实主体来自图谱三元组，大模型只组织语言、不改写事实；图谱未覆盖到的小节（例如某个病害的"物理防治""生物防治"）会**再补一次请求、由大模型按通用农技常识补齐**，并在那一行明确标注「以下由大模型按通用农技常识补充（非本图谱数据）」，跟图谱事实分得清清楚楚（见 `core/answer_filler.py`）；防治建议按「农业防治 → 生物防治 → 物理防治 → 化学农药」绿色防控顺序输出，并带安全间隔期；杂草与病害分开建类 |
| **方案的可操作性** | 不只是"建议施钾肥"，而是"你今天在第 201 天、处于灌浆期第 22 天、还有 15 天收获"；处方带具体肥料名称与养分含量、施用方式、安全间隔期；生产规划含茬口与风险提示 |
| **交互体验** | 检索联想 220ms 防抖、点击候选即定位、双击下钻、1/2 跳切换、面包屑回溯、Esc 返回、移动端自适应；物候页填一次日期就长期自动提醒 |
| **知识检索的准确性** | 三重保障：① 实体识别按名称长度优先匹配避免短名误命中；② 意图识别采用关键词加权 + 实体类型纠正；③ 每条回答附 `sources` 溯源可复核；物候推算不用大模型，结果确定可复现 |
| **从"查得到"到"用得上"** | 不只返回关系列表，而是组织成可直接照做的**处方**（哪天施肥、用什么药、间隔几天、能不能种） |

## 七、常见问题

**Q：Neo4j 连不上？**
检查 7687 / 7474 端口是否监听，`config.py` 中的账号密码是否正确。系统对连接失败有兜底：`get_all_crops` 等原方法返回空列表，新方法返回空结果，页面显示"暂无数据"而不崩溃。

**Q：拍照识病要不要单独配一个视觉模型？**
当前不用。豆包 `doubao-seed-2-1-pro` 原生多模态，图文共用一个模型，
`LLM_VISION_*` 留空会自动复用主模型。只有把主模型换成纯文本模型（如 `deepseek-chat`）时，
才需要另配一个"看得见"的模型（见「拍照识别病虫害」一节的配置表）。
未配置时**不会假装识别成功**：识别请求返回明确失败原因，用户可改用「填写症状描述」。

**Q：为什么豆包回答有时候很快、有时候要等十几秒？**服务端延迟本身有波动（实测连续 6 次同样的短请求：
`10.1 / 4.1 / 2.1 / 超时 / 1.7 / 23.0` 秒）。程序已经做了两件事兜底：
超时放宽到 90 秒、失败自动重试 2 次。另外豆包默认会输出一段"思维链"，
关掉后同一个问题从 27.9 秒降到 4.4 秒 —— 这个已默认关闭。

**Q：图片会不会留在服务器上？**
不会留**原图**：图片只在内存中压缩、转 base64 后发给模型。
但为了让「历史记录」能回看"上次拍的是什么"，会另存一张**压缩到长边 480 的小图**
（约 40~60KB，路径在 `static/uploads/diag/`），删掉那条记录时这张小图也会一起删除。

**Q：管理端里"能种植什么"是空的，只有一句"作物列表加载失败"？**
作物清单读自图谱（Neo4j）。先看提示里的原因：
写了"未连接 / Driver closed"就是图谱连接的问题 ——
① 确认 Neo4j 在运行（双击根目录 `一键启动.bat` 会自检并顺手拉起来）；
② 点提示里的「**重新加载**」即可，不用刷整页。
若是"没读到带生育期数据的作物"，则是图谱数据被清空过，用
`python scripts/08_import_extended_kg.py` 重新导入。
> 这个位置曾经有个隐蔽 bug：登出会关掉全局 Neo4j 连接，导致登出一次后
> 作物下拉全空、只能重启服务。现已修（见「管理端 / 用户端」一节末尾）。

**Q：不配大模型能演示吗？**
可以。四类处方全部由图谱结构化生成，内容完整（含表格）。配置后语言更口语化。

**Q：怎么确认模型接对了？**
走接口：`GET /api/llm/status`（只看配置，不回显密钥）、`POST /api/llm/test`（真发一条最小请求）。
**界面有意不显示模型名与厂商名**（详见「大模型接入」一节）。
后端控制台会打印 HTTP 状态码与原始返回，便于排障。

**Q：想换成 WorkBuddy 里用的那个模型？**
把 WorkBuddy「设置 → 模型 → 自定义模型」里的**接口地址 / API Key / 模型名称**三项，
对应填入 `code/config_local.py` 的 `LLM_BASE_URL / LLM_API_KEY / LLM_MODEL` 即可。
WorkBuddy 客户端本身不对外提供 API 服务，它是模型调度器 —— 它调度谁，本项目就接谁。

**Q：想恢复成原来的纯原库数据？**
```bash
python import_agri_kg_to_neo4j.py     # 原脚本仍可用（会清库后导入原 2558 条）
```
> 已给该脚本加了防误清保护：检测到库里有扩展图谱节点时会先警告并要求输入 `yes`
> 确认（非交互环境需显式加 `--yes`）。**别在演示前误跑它**，否则扩展图谱会被清掉，
> 重跑 `python scripts/08_import_extended_kg.py` 即可恢复（约 10 秒）。

**Q：图表依赖被墙了？**
`static/` 下已放 `echarts.min.js` 与 `vis-network.min.js`，页面优先加载本地文件，CDN 仅作兜底，**完全离线可用**。

**Q：如何验证图谱规模？**
